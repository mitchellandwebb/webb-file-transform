

One model of language that we have, is specifying _what_ transforms we want to transform, and _how_ we want to transform them. There might be various ways to perform the transform, but the simplest way to is to take the file, read the entire string, and then transform that string before sending it back to the _same_ file. But we might also want to send the output to a different file, or to modify the extension as part of the transform.

Querying also has variation. We might want to query by extension, or by filename, or by regexp, with the possibility of exclusion (maybe). Although for now, exclusion isn't all that important. And we want to query _within_ a particular directory, and do so recursively, to find all the matching files of interest.

So we need a way to query paths starting from a particular directory, at minimum. The paths can then be transformed to files, as needed. Files also need to be transformed in several ways: 

- Transform the extension ( as new file)
- Transform the content
- Move the file

How do we express these possibilities? Is it enought to use `mv` and 'cp', or should we seek something else?

An in-place file transformation is not difficult. Read all the text. Close the file. Truncate it. Write the transformed text.

Transforming the extension is less clear. But almost always, we want a _new_ file with the _new_ extension, but the same name, to have the file. But since we're transforming the whole file, it seems de-facto true that any existing file with that name, at that location, is necessarily deleted or at least truncated.

And it's ... rarely the case that we want to _move_ the file. Moving isn't a transforming operation; it's something that is done _after_ the transform. So it doesn't belong here. No; a transform is based on (A) transforming the text, and (B) deciding where the transformed data goes. This is one complete operation; we can't have it sitting in memory for _all_ files; so we either have to _stream_ each action -- locking until the prior action is complete -- or the action itself has to be included. This is a ... decent use case for channels, at minimum, to separate actions out to separate processes. And it's a generalization of pipes -- but we could also just use pipes, and not channels. The problem ... is that the pipes that we have in Purescript are ... a bit shit in terms of usability. I look at them, and the model is still a bit shit, in the sense that I don't easily see what I'm supposed to be doing.
  Just .. yielding values, and awaiting values, I suppose. The difference, perhaps, is in the fact that where a simple Aff returns all values at once, a Pipe, or Conduit, or Flow describes operations that are occurring over multiple values. And so what that means ... is that for any operation, we have to describe in relatively bizarre ways. But this still feels more like simulation and not like a model.
  
We could just use Channels. A channel represents a suspension in computation; and it represents multiple values. In that sense, a pipe just represents a channel composed with a receiving function within an Aff-like monad; the receiving function is thus of an input type and has commands to produce one or more output types, but once it ends, it is ready to receive again. In that sense, connecting pipes together is easy, although all these pipes are actualized -- they aren't repeatable computations in this case; we've actually created a physical channel, rather than a description of one. But this is ... a good thing, perhaps. That means our models return concrete _other_ models as their base, and functions that produce these other models can be _lifted_ into a describing function, if desired. Whereas relying entirely on these abstract monads stops us from ever just ... _doing_ anything properly. Or so it seems to me. It also gives me more tools, generally-speaking.

Hmm. So we have channels now. But they're not ... exactly safe. It's hard to draw a comparison in my mind to Pipes. Each Pipe's monad enables writing the monad to await and yield values, as a Node in the pipeline. The node then runs from start to bottom; when yielding, a node starts the next node's execution until the next node's next suspension point or yield; when awaiting, a node resumes the previous node's execution until its next suspension point or yield. Pipes can be connected end to end, to yield a machine that essentially executes syncronously, even though each portion is responsible for a separate piece of the output stream. And that's very cool, and quite awesome; in much the same way, Channels can enable something similar, though it will be relatively asyncronous in execution, and each process is ... potentially more independent by comparison. That's not necessarily a bad thing.

But I'm still not quite sure how to represent streams of values. Pipes are certainly one means of doing so, but because they have an Input and Output, there's no way to compose them monadically -- and composing them end to end to produce a final Pipe ensures that _all_ pipes are fully consumed and filled with input. That might well be the best way, even if the abstraction of the Pipes library is _too_ abstract for my ordinary usage.
  But the trouble with pipes is that it isn't a monad, and I'm not sure why. I mean, it's clear why it isn't a monad -- rather, each pipe's operation is a monad, which makes sense -- it's a program working with specific kinds of values, and describing how a prior action produces the next action within the node of a pipe. But in composing this as a monad, and connecting pipes by type-matching, we lose higher levels of expression, like the ability to catch errors, or talk about cancellation of the pipeline. Maybe that's just how it has to be.
